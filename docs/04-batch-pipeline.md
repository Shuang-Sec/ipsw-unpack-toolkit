# 04 · 批量解包的工程实践

单次解包不难，难的是**跑几百次不出错**。本文记录实际长跑中总结的做法。

## 四阶段流程

```
① 查地址     ipsw.me API                    → IPSW 直链
② 远程提取   ipsw extract --remote          → 解密后的 APFS dmg
③ 解包       fake-apfs-fuse（7-Zip）        → dyld shared cache 文件集
④ 修复       decmpfs_fix.py（zbm）          → 补齐透明压缩文件
```

每阶段都可能因网络、磁盘、上游工具而失败，所以批处理脚本要能**从任意阶段恢复**。

## 四种保护机制

### 1. 断点续跑

判断依据用**产物**而不是状态文件 —— 状态文件会与实际产物脱节：

```bash
if [ -d "$D" ] && [ "$(ls "$D" | wc -l)" -gt 10 ]; then
  echo "复用已解包缓存"; exit 0
fi
```

> 这一条是踩过坑的：早期版本记录了"已完成"清单，但产物实际没落盘（脚本里少了一句移动），
> 导致**日志显示正常、目录却是空的**。改用产物本身判断后，这类问题不可能再隐藏。

### 2. 失败重试

网络抖动很常见，每个组合最多试 2 次，中间清理临时目录并短暂等待。

### 3. 卡死保护

`ipsw` 偶发卡住（CPU 0%、文件不增长）。用 `timeout` 兜底：

```bash
timeout 900 ipsw extract --dyld --remote "$URL" -o "$OUT"
```

> 注意配合进程清理，避免残留的下载进程占住带宽。

### 4. 磁盘保护

磁盘是长跑最容易爆的资源。每轮开始前检查剩余空间，低于阈值就清理：

```bash
AVAIL=$(df --output=avail -k "$WORK" | tail -1 | tr -d ' ')
[ "$AVAIL" -lt 7000000 ] && rm -rf "$WORK"/dsc_* "$WORK"/tmp
```

## 磁盘峰值控制

固件动辄 8–11 GB，而 dmg 解出来后还有一份解包内容。控制手段：

| 手段 | 效果 |
| :--- | :--- |
| `--remote` 只拉所需区间 | 传输 10.7 GB → 约 5 GB |
| 只解 dyld 目录（跳过整卷） | 解包 3.8 GB → 约 520 MB |
| **解完立即删除源 dmg** | 峰值从"dmg + 内容"降为 max(两者) |
| `TMPDIR` 指向工作盘 | 避免 tmpfs 被撑爆（`EDQUOT`） |

实际长跑中峰值稳定在 **约 5 GB**。

## 实测性能

以 670 个"机型 × 版本"组合的长跑为例：

| 项 | 值 |
| :--- | :--- |
| 单组合耗时 | 约 2.4–2.7 分钟 |
| 总组合数 | 670 |
| 总耗时 | 约 17 小时（串行） |
| 失败数 | 0 |
| 网络占比 | 约 70–80% |

**瓶颈在网络**。若要提速，方向是并发下载 + 串行解包，而不是优化解包本身。
